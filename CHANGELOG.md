# Changelog

All notable changes to this project are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project
adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Breaking

- The build option `oauth` is gone: `clearance.oauth` is always declared, and uplink, a lazy dependency, is fetched with clearance and compiled only in a program that imports `clearance.oauth`. An option on a library splits it: a program where one package took clearance with `.oauth = true` and another without it held two clearance modules of one file, which Zig refuses. Migration: drop `.oauth = true` from `b.dependency("clearance", ...)`; a project that took `clearance` alone now fetches uplink too, and builds nothing more.
- `jwe.EncryptError`, `oauth.request_object.Error` and `oauth.client_auth.Error` carry `std.Io.Cancelable`: a cancel that lands while an ECDH-ES ephemeral key is drawn (cloak's `PrivateKey.generate`, which returns it since cloak c4d7357) is returned as `error.Canceled`, through `jwe.encrypt`, a request object's write and every client authentication that signs one. Migration: a `switch` on one of them adds `error.Canceled`. uplink 7e01d22 -> 1002577, which brings cloak 5103da0 -> c4d7357 and aegis c8982a8 -> c43e90d with it.
- A `RemoteKeySet` fetch whose task is canceled is no fetch's outcome. Its own caller gets `error.Canceled`, as before. The tasks waiting on it no longer take the set held, the last error or `Unavailable` from it: one of them fetches, and the others go on waiting for that fetch, each until its own cancel, within the cooldown between attempts. A caller that read `Unavailable` from `lease` or `verify` while another task's fetch was canceled now gets a fetched set; nothing to change in code.
- A caller's replay set and token store can say a wait was canceled. `jwt.Replay.RecordError` is `error{Full} || std.Io.Cancelable`, and `TokenStore.forgetFn` (and `TokenStore.forget`) returns `std.Io.Cancelable!void`. A set or store kept on a disk or over the network returns `error.Canceled` from them; one in memory never does. `dpop.VerifyError` and `logout.VerifyError` gain `Canceled`, which `verifyProof` and `verifyToken` return where the replay set's record was canceled (it was `ReplayFull`). Write `try store.forget(io, key)` where `store.forget(io, key)` was, and return `std.Io.Cancelable!void` from a `forgetFn`.
- `dpop.Session.proof` (and `headers`) refuse a target that is no request URI a proof can name as its `htu` (RFC 9449 section 4.2: not an absolute https URL, http to the loopback alone, or one with a fragment) with `error.InvalidTarget`, a new member of `ProofError`, where the proof was signed over it without a nonce. A token request to such an endpoint fails as `InvalidEndpoint`, as its fetch would.
- `token.Grant` gains `device_code`, and `errors.Code` gains `authorization_pending`, `slow_down`, `expired_token` and `unsupported_token_type` (which was `other`, the bearer check's introspection refusal among them), `invalid_dpop_proof` and `use_dpop_nonce`: a switch over either needs the new cases.
- `AuthorizationFlow.BeginError` gains `PushRequired`.
- `oauth.bearer.Verifier.check` takes the request (`bearer.Request`: its `Authorization`, its `DPoP` fields, method and URL) where it took the `Authorization` value; `bearer.bearerToken` is `bearer.credentials`, which reads `DPoP` as well as `Bearer`. `access_token.verify` refuses a bound token as before unless `Expected.binding` names what the request proved. `oauth.token.TokenType` gains `dpop`, `jws.Check` gains `request`, `binding`, `nonce` and `replay`; `jws.SignError` gains `InvalidHeader` and `InvalidPayload`; a header with `crit` naming `b64` is now read (and refused unless `Options.unencoded`), and one with `b64` outside `crit` is `InvalidHeader`; and `fetch.postForm` takes the request's `DPoP` value.
- `access_token.Binding` is a struct (`dpop`, `mtls`, either or both) where it was a union: a request may prove a DPoP key over mutual TLS, and an unbound token over mutual TLS passes (RFC 8705 binds only what `cnf` names) where it was refused. `AuthorizationFlow.begin` takes an allocator (a request object is signed with it), and `BeginError` and `PushError` gain `SignedRequestRequired`; `client_auth.Method` and `Credentials` gain `tls_client_auth` and `self_signed_tls_client_auth`, and `client_auth.Error` gains `EntropyUnavailable` (an encrypted request object's ephemeral key). `Algorithm` gains `es512`; a P-521 JWK is read where it was skipped as unsupported.
- JWE: `jwt.VerifyError` (and with it `id_token.VerifyError`, `access_token.VerifyError` and `logout.VerifyError`) gains `Encrypted`: a compact JWE handed to `verify` is refused by name, as the nested JWT `verifyNested` reads (below), where it was `Malformed`; `oauth.userinfo.ReadError` gains `InvalidEncryption`; `jws.Check` gains `compression`, `pbes2` and `decryption`. `jwk.Options`, `PrivateOptions` and `readPublic` take a `purpose` (`.signatures`, the default, or `.encryption`): a key read for one is never used for the other, and a set read for encryption leaves out keys for signatures (`Skip.not_for_encryption`). `jwk.PrivateError` gains `NotForDecryption`, `jwk.PublicError` gains `NotForEncryption`; `Key` gains `management`, `content`, `encrypt` and `decrypt`, and `Key.Material.okp` its `curve`.
- `Algorithm` gains `ml_dsa_44`, `ml_dsa_65` and `ml_dsa_87`, `Algorithm.Family` gains `akp`, and `Key.Material` gains `akp`: a switch over any of them needs the case. A key set's AKP keys (RFC 9964) are read where they were left out as unsupported.

- `jwt.Replay` and `oauth.TokenStore` are interfaces a type embeds and finds itself from by `@fieldParentPtr`, where they were a context pointer and a vtable: `MemoryReplay.replay` and `store.Memory.store` are fields (`&set.replay`, `&memory.store`) where they were functions, and a `Replay` or `TokenStore` is taken by pointer (`dpop.Expected.replay`, `logout.Expected.replay`, `bearer` options' `replay`, `flow.fresh`'s `tokens`).
- Pins uplink main 7e01d22: a cancel that lands while a response drains its unread body at `deinit` stays asked for, where uplink dropped it, so every fetch's release keeps a cancel it met.
- Pins cloak main e7c45f4 (its interfaces carry no context pointer, and it links on x86_64 Windows), uplink's car 7f85e60, which takes them, and shakedown 0.6.0.
- Pins aegis 0.2 (0.2.3), strand 0.15 and cloak 0.23's line: the shared caches (`MemoryReplay`, `store.Memory`, `dpop.Session`, `Introspector`, `RemoteKeySet`) hold their state in aegis `BlockingGuarded` owners, so a field that was guarded by a mutex is reached through the owner.

- The declarations the entries above change, by name. `clearance.oauth.TokenStore` and `clearance.oauth.store.TokenStore` are embedded (`clearance.oauth.store.TokenStore` requires its functions): `clearance.oauth.TokenStore.ptr`, `clearance.oauth.TokenStore.vtable`, `clearance.oauth.TokenStore.VTable`, `clearance.oauth.store.TokenStore.ptr`, `clearance.oauth.store.TokenStore.vtable`, `clearance.oauth.store.TokenStore.VTable` and their fields `clearance.oauth.TokenStore.VTable.forget`, `clearance.oauth.TokenStore.VTable.load`, `clearance.oauth.TokenStore.VTable.save`, `clearance.oauth.store.TokenStore.VTable.forget`, `clearance.oauth.store.TokenStore.VTable.load`, `clearance.oauth.store.TokenStore.VTable.save` are gone; `clearance.oauth.TokenStore.forget`, `clearance.oauth.TokenStore.load`, `clearance.oauth.TokenStore.save`, `clearance.oauth.store.TokenStore.forget`, `clearance.oauth.store.TokenStore.load`, `clearance.oauth.store.TokenStore.save` take `*TokenStore`, and `clearance.oauth.store.Memory.store` is the embedded field. The shared caches' state is held by aegis guards, each lock ranked by an aegis `Order` of its own: `clearance.oauth.Introspector.mutex`, `clearance.oauth.store.Memory.mutex`, `clearance.oauth.RemoteKeySet.mutex`, `clearance.oauth.RemoteKeySet.current`, `clearance.oauth.RemoteKeySet.fetching`, `clearance.oauth.RemoteKeySet.last_attempt`, `clearance.oauth.RemoteKeySet.last_error` are gone into `clearance.oauth.Introspector.entries`, `clearance.oauth.store.Memory.sets` and the key set's guarded state, and `clearance.oauth.RemoteKeySet.fetched` is an aegis `Condition`. `clearance.oauth.RemoteKeySet.Lease.snapshot` names `clearance.oauth.RemoteKeySet.Snapshot`, now public. `clearance.oauth.bearer.Extracted` (`clearance.oauth.bearer.Extracted.malformed`, `clearance.oauth.bearer.Extracted.none`, `clearance.oauth.bearer.Extracted.token`) and `clearance.oauth.bearer.bearerToken` are gone with the `bearer.Request` check above.
- The error sets that grew, by name: `EntropyUnavailable` (a random draw the system refused) in `clearance.oauth.client_auth.formRequest`, `clearance.oauth.introspection.request`, `clearance.oauth.token.request`, `clearance.oauth.AuthorizationFlow.BeginError`, `clearance.oauth.AuthorizationFlow.FinishError`, `clearance.oauth.AuthorizationFlow.begin`, `clearance.oauth.AuthorizationFlow.finish`, `clearance.oauth.AuthorizationFlow.verifyIdToken`, `clearance.oauth.FreshError`, `clearance.oauth.IdJagError`, `clearance.oauth.Introspector.Error`, `clearance.oauth.Introspector.introspect`, `clearance.oauth.RedeemError`, `clearance.oauth.RefreshError`, `clearance.oauth.TokenError`, `clearance.oauth.RemoteKeySet.VerifyError`, `clearance.oauth.RemoteKeySet.verify`, and `clearance.oauth.AuthorizationFlow.begin` takes an allocator; JWE's errors in `id_token.verify`, `jwt.verify` and `jwk.PrivateKey.parse` (`NotForDecryption`); `InvalidHeader` and `InvalidPayload` in `jws.sign`, `jwt.sign` and `jwt.SignError`. `clearance.oauth.fetch.postForm` takes the DPoP proof. ### Added

- `base64url.encodeInto(out, bytes)`: the encoding written into the start of `out`, which holds `encodedLength(bytes.len)` bytes, with no writer and nothing to fail.
- A property for the Design's "the verifier picks the key": over keys of any kids and algorithms and tokens signed by any of them, a token verifies exactly when its algorithm is one the verifier names, its `kid` (or, without one, its algorithm alone) leaves one key that fits, and that key signed it. It fails on each of three planted faults (a key's own `alg` ignored, the first of two candidates taken, the header's `kid` ignored).

- `clearance.time`: a timestamp's NumericDate (RFC 7519 §2) as aegis's `Instant(.real, .second, i64)`, which every claim check reads `now` through.
- Device authorization (RFC 8628): `oauth.device` writes the request and reads the answer into an `Authorization` (the device code in wiped memory; `verification_uri` and `verification_uri_complete` held to HTTPS or loopback, since a person is sent there; a `user_code` of at most 64 bytes with no control characters, since it is printed to a terminal; Google's `verification_url` read when `verification_uri` is absent; the interval 5 s when absent, never below 1 s); `token.Grant.device_code`; metadata's `device_authorization_endpoint`. `oauth.DeviceFlow`: `begin` asks for the codes, `poll` makes one token request (`pending`, `slow_down` with the interval grown by 5 s, the tokens, or the refusal), `wait` polls at the interval on `io`'s sleep until the person finishes, the server refuses, or the codes would expire first (`error.Expired`, nothing sent). A property over the answer; a bench row.
- Token revocation (RFC 7009): `oauth.revocation` writes the request (the token, its `token_type_hint`, the client's authentication) and reads the answer (any 2xx is the token revoked, whatever its body; another status is the server's error, a 503 among them, never retried); metadata's `revocation_endpoint` and its auth methods; `oauth.revoke` sends it. A sign-out revokes the refresh token, which ends the grant at the server, then forgets the store's entry. A property, a bench row.
- DPoP (RFC 9449). `clearance.dpop` (the JOSE module, no uplink): `writeProof` signs a proof of a request (`typ` `dpop+jwt`, the public key as the header's `jwk`, `jti`, `htm`, `htu` without query or fragment, `iat`, `ath` for a presented token, the server's `nonce`); `verifyProof` checks one as §4.3 asks: an allowed asymmetric algorithm, the signature by the key its header carries (the one place a header's key is used, and only for its own proof; private and secret keys refused), `htm`, `htu` compared after RFC 3986's normalisation, `iat` within `max_age` (60 s) and the leeway, `ath` in constant time, the nonce, and the `jti` recorded in a replay set; it returns the key's thumbprint. `jwt.Replay` (an interface) and `jwt.MemoryReplay` (fixed places, never allocating once made, refusing when full rather than forgetting) keep single-use identifiers, by `jwt.replayId`'s hash. `access_token.Expected.binding` holds a token's `cnf` to a DPoP key's thumbprint or a certificate's hash; introspection reads `cnf`'s `jkt` and `x5t#S256`. `jws.SignHeader.jwk` writes a public key into a header, `jws.Header.jwk` exposes it raw (never used to choose a key), `jws.verifyKey` verifies against one key; `jwk.writePublic` and `jwk.readPublic`. `clearance.oauth`: `dpop.Session` (the key, each server's last nonce per origin) proves every token request when `TokenOptions.dpop` is set, learns a `DPoP-Nonce` and sends a refused request once more with it, reads `DPoP` tokens (refused when no proof was sent), refuses to refresh a bound set without its session, binds the code with `dpop_jkt` (`AuthorizationFlow.Begin.dpop`), and writes a resource request's `Authorization: DPoP` and proof (`Session.headers`). `bearer.Verifier.dpop` takes DPoP tokens with their proofs (the token held to the proof's key, a replay refused, a bound token sent as Bearer refused, the resource's nonce asked for with `use_dpop_nonce` and `Refusal.dpop_nonce`), answering with both challenges (`challenge.Bearer.scheme`, `algs`; `challenge.readScheme`). A property over proofs; bench rows for a proof signed and verified.
- Pushed authorization requests (RFC 9126): `oauth.par` writes the push (the authorization parameters with the client's authentication, `client_id` once) and reads its 201 (a printable `request_uri` of at most 1 KiB, kept inline, and its expiry); `authorize.Params` is the one list of parameters both the URL and a push are written from; `authorize.writePushedUrl`; metadata's `pushed_authorization_request_endpoint` and `require_pushed_authorization_requests`. `AuthorizationFlow.push` pushes (with a DPoP proof and its nonce retry when `TokenOptions.dpop` is set) and writes the short URL; `finish` reads its redirect as for `begin`, which now refuses a server that requires pushes (`error.PushRequired`). A property, a bench row.
- OpenID Connect UserInfo (Core §5.3): `oauth.userinfo.readResponse` reads the answer into the caller's claims (`userinfo.Standard` holds Core §5.1's), the answer's `sub` held to the ID token's, a required argument (a substituted answer for another user otherwise passes); a signed answer (`application/jwt`, when the client registered one) verified with the caller's keys and algorithms, its `iss` and `aud` held to the issuer and the client when present; JSON where a JWT was expected, or the reverse, refused; a refusal read from the `WWW-Authenticate` challenge, else the error body. `oauth.fetchUserInfo` asks the metadata's `userinfo_endpoint` with the set's token, Bearer or DPoP with its proof (sent once more with the resource's nonce). `fetch.getProtected`, and `fetch.Answer`'s `content_type`, `challenges` and `dpop_nonce`. A property, a bench row.
- OpenID Connect logout. `clearance.logout.verifyToken` verifies a Back-Channel Logout 1.0 token as §2.6 asks: signed by the provider's keys with an allowed algorithm, typed `logout+jwt` (or untyped, or `JWT`), `iss` the provider, `aud` the client, `iat`, `exp` and `jti` present, the back-channel event as an object, a `sub` or a `sid`, no `nonce` (so no ID token passes for one), and the `jti` recorded in a `jwt.Replay` until `exp`. `oauth.logout`: `writeUrl` (RP-Initiated Logout 1.0: `id_token_hint`, `logout_hint`, `client_id`, `post_logout_redirect_uri`, refused without a hint or client to check it against, `state`, `ui_locales`), `readBackChannel` (the request's one `logout_token`), `readFrontChannel` (`iss` and `sid` together, `iss` the provider's, required when the client registered it). Metadata's `end_session_endpoint` and the four logout support flags; registration's `post_logout_redirect_uris`, `backchannel_logout_uri`, `frontchannel_logout_uri` and their session flags. Properties over tokens and requests; a bench row.
- JWS in the JSON serializations (RFC 7515 §7.2) and unencoded payloads (RFC 7797). `jws.verifyJson` reads a general or flattened document (by its shape; both at once refused) and verifies when one of its signatures verifies with a key the caller's set gives for its headers: `Verified.index` names it, `Verified.protected` holds its decoded protected header (ACME's `nonce` and `url` read from it), `Verified.unprotected` its unprotected header raw, never trusted beyond the `kid` that chose the key. Every signature's `alg` must be protected (an unprotected one, RFC 7520 §4.7's example among them, is refused by decision), its two headers' names disjoint (§7.2.1), `crit` and `b64` protected; at most 16 signatures; the most telling refusal is returned. `crit` is understood (non-empty, unique, no registered name, every name present): `b64` alone, and only with `Options.unencoded`, as RFC 7797 §7 asks. `Options.detached_payload` verifies a payload sent apart (RFC 7515 Appendix F), compact (`scratchLengthDetached`) or JSON (`scratchLengthJson`). `jws.signJson` writes both serializations, `jws.signCompact` a detached compact token, `SignHeader.b64` an unencoded payload (refused with a `.` in the compact form), `SignHeader.extra` more protected members (a name clearance writes, or one twice, refused). The JOSE cookbook's §4.4 to §4.8 and RFC 7797 §4's examples pass, written byte for byte where the signature is deterministic. A property over documents; bench rows.

- JWE (RFC 7516, RFC 7518 §4 and §5), the safe subset. `jwe.decrypt` reads the compact serialization and both JSON ones (by shape), with keys the caller holds (`jwe.DecryptionKey`: a private RSA, EC or X25519 key read from a JWK, an `oct` secret, or a password), under two allowlists with no default (`key_algorithms`, `encryptions`), and returns the joint header, the plaintext in the caller's scratch and the recipient's index. `jwe.encrypt` writes any serialization to one recipient or several (an RSA, AES or password recipient, `aad`, unprotected headers). Key management: RSA-OAEP, RSA-OAEP-256, -384, -512, A128KW, A256KW, `dir`, ECDH-ES and ECDH-ES+A128KW and +A256KW on P-256, P-384 and X25519 (encryption under an ephemeral key cloak generates per message, its public half the header's `epk`), A128GCMKW, A256GCMKW, PBES2-HS256+A128KW and PBES2-HS512+A256KW. Content: A128GCM, A256GCM, A128CBC-HS256, A256CBC-HS512. Refused by construction: RSA1_5 and every 192-bit AES variant (no value spells them; std has no AES-192), `zip` anywhere (decompression bombs and the compression oracle), a PBES2 count past `max_pbes2_count` (10 000) or a salt under 8 bytes, an `epk` off the recipient's curve, X25519's all-zero secret, and a key the token names (`jku`, `jwk`, `x5u`, `x5c` are never read). A failed key recovery goes on with a random content key (RFC 7516 §11.5): one `DecryptionFailed` for every cryptographic failure, the check named in `Diagnostics`. The cookbook's §5.1 to §5.13 decrypt (§5.1 and §5.9 refused), §5.3 and §5.6 to §5.8 encrypt byte for byte from their generated values, §5.4's content key wraps byte for byte under its ephemeral key, and Wycheproof's `json_web_encryption` passes, its RSA1_5 and A192 groups not offered. `jwk` reads keys for encryption: RSA, EC and X25519 (RFC 8037 §3.2) private keys, `oct` secrets, and public keys to encrypt to, a JWK `alg` naming a JWE algorithm binding the key to it.
- Nested JWTs (RFC 7519 §5.2), an operation of their own, as the caller registered them: `jwt.verifyNested` and `id_token.verifyNested` (OpenID Connect Core §10.2) take an encrypted token and a `jwt.Decryption` (the keys and JWE allowlists), decrypt it, then run `verify`'s checks on its content; a signed token alone is refused (`NotEncrypted`), so an answer that should have come encrypted is never taken without it, and a `cty` other than `JWT` is `WrongType`. `verify` takes no decryption. `AuthorizationFlow.verifyNestedIdToken` is `verifyIdToken`'s nested form. `jwt.decryptNested` is the decryption step alone. `oauth.userinfo.readEncryptedResponse` and `UserInfoOptions.encrypted` read an encrypted answer: the claims as JSON, or the signed JWT when signing was registered too; `readResponse` refuses one (`WrongForm`). Each takes the `io` the decryption draws from as an argument of the call; a `jwt.Decryption` holds none.
- Mutual TLS (RFC 8705). `tls_client_auth` and `self_signed_tls_client_auth`: the certificate the HTTP client presents authenticates, `client_id` in the body; `Client.mutual_tls` for a public client asking for bound tokens. Metadata's `mtls_endpoint_aliases` and `tls_client_certificate_bound_access_tokens`; `AuthorizationServer.endpoint(which, mutual_tls)` picks the alias, and every request the flows send (token, PAR, device, revocation, UserInfo, registration) goes through it. Certificate-bound tokens at a resource: `bearer.Request.client_certificate` (uplink's `server.Request.peer_certificate`) is hashed and held to the token's `cnf.x5t#S256`, on the JWT path and introspection's alike, through the one check `access_token.holds`. Registration's `tls_client_auth_*` and `tls_client_certificate_bound_access_tokens`.
- JWT-Secured Authorization Requests (RFC 9101). `oauth.request_object.write` signs the authorization parameters as a request object (`typ` `oauth-authz-req+jwt`; `iss` the client, `aud` the issuer, `iat`, `nbf`, `exp`, `jti`; `resource` an array when several), and encrypts it to the server when asked (signed, then a compact JWE, `cty` `JWT`). `authorize.writeSignedUrl` sends it by value (`client_id`, `request`, and `response_type` and an OpenID Connect `scope` repeated, Core §6.1); `par.requestObject` pushes it. `AuthorizationFlow.Begin.request_object` does either from `begin` or `push`, signing anew for each push sent; a server listing `require_signed_request_object` is refused a plain request. Metadata's and registration's request object members, and OpenID Connect's encrypted ID token and UserInfo registration members.
- Properties over JWE documents (no mutation decrypts to other content) and nested tokens; bench rows for JWE decryption and encryption (ECDH-ES+A128KW on P-256 among them) and a nested ID token.
- ES512 and P-521 (RFC 7518 §3.4). `Algorithm.es512` verifies and signs (r || s, 132 bytes) on P-521 keys, which JWK sets, private JWKs and public JWKs now read (66-byte coordinates, the point checked by cloak's `checkEc`) where they were left out as unsupported; `jws.Signer.fromJwk` picks ES512 for a P-521 key; JWE's ECDH-ES and its key wraps run on P-521 too (`DecryptionKey.PrivateKind.p521`). The cookbook's §4.3 verifies and its key signs; Wycheproof's P-521 JWS cases pass.
- ML-DSA in JOSE (RFC 9964): `ML-DSA-44`, `ML-DSA-65` and `ML-DSA-87` verify and sign, pure ML-DSA with the empty context, on cloak's ML-DSA. AKP keys are read from key sets and public JWKs (`alg` required and one of the three, `pub` exactly its level's length; for signatures only) and written with their thumbprint members `alg`, `kty` and `pub` (RFC 9964 §6); a private AKP JWK is read by its 32-byte seed (`priv`, the one form RFC 9964 defines), the public key derived from it and compared with `pub`, and `Signer.fromJwk` signs with its own `alg`. RFC 9964 Appendix A.1's three examples verify, their `kid`s are their keys' thumbprints, and ML-DSA-44's signature is the deterministic one over its signing input. Bench rows `jwt/sign-ml-dsa-65` and `jwt/verify-ml-dsa-65`.
- Properties over the certificate and DPoP binding (any `cnf` against any proof passes exactly as RFC 8705 §3 and RFC 9449 §7.1 say) and over request objects (any authorization request verifies and carries its parameters back); bench rows for ES512 signing and verification and a request object written.

- aegis 0.3: a remote key set's wait for its fetch is its guard's (`guard.wait(&condition, io, .none)`). Pins aegis breaking-0.3 (a34e694), and on it strand (cc6918d), cloak (5103da0), uplink main (a051420) and shakedown main (4979fa9), the commits relic main pins.

### Fixed

- The JSON serializations follow one rule: `recipients` (JWE) or `signatures` (JWS) selects the general syntax, which reads only the members RFC 7516 §7.2.1 or RFC 7515 §7.2.1 define and ignores every other top-level member; without it the document is flattened. `jwe.decrypt` refused a general JWE with a top-level `header` or `encrypted_key` beside `recipients` as `Malformed`, and `jws.verifyJson` a general JWS with a top-level `signature`, `protected` or `header` beside `signatures`; the RFCs define neither member in the general syntax (§7.2.2 forbids `recipients` and `signatures` in the flattened one, so there is no ambiguity), and a member they do not define MUST be ignored. go-jose v4's `FullSerialize` writes recipient 0's `encrypted_key` at the top level too, so its general JWE was refused (trials' JOSE exchange); it decrypts now, each recipient with its own key, and a top-level `encrypted_key` other than recipient 0's, or of another type, changes nothing. `payload` is the one payload either way.
- `DeviceFlow.wait` lets the full interval pass on the awake clock before each poll, as RFC 8628 section 3.5 asks. A timed wait can end up to a timer tick before its deadline (Windows times it on interrupt time, which runs apart from the awake clock), so a poll could go out a few milliseconds early and draw `slow_down`.

## [0.4.0] - 2026-10-21

### Breaking

- Pins uplink 0.8.7, cloak 0.19.0 and aegis 0.1.14 (were 0.8.1, 0.14.0 and 0.1.11): a build with clearance moves to those lines, and `jws.Signer.private` takes cloak 0.19's `PrivateKey`.
- A JWK's RSA public key gets cloak's checks for every RSA public key: 2048 to 4096 bits, minimal integers, an odd exponent of 3 to 2^32-1 (an exponent of 5 to 8 bytes was read), and no ROCA fingerprint (CVE-2017-15361). Wycheproof's `json_web_key` tcId 7 and `json_web_crypto` tcId 46 now pass, where they were named divergences.
- An `oct` key whose `k` holds a JSON escape is left out as invalid: no base64url text needs one, and the unescaped copy would sit outside wiped memory.

### Added

- `jwk.PrivateKey.parse`: a private JWK read for signing (RFC 7518 §6.2.2 and §6.3.2, RFC 8037 §2): EC P-256 and P-384, Ed25519, and two-prime RSA keys with their CRT members, made by cloak's `PrivateKey.fromComponents` through the checks a parsed key gets (the public half derived and compared). The document is read from a wiped copy and the private members decoded into wiped memory, both erased before it returns; `public` is the public half with the JWK's `kid`, `alg`, `use` and `key_ops`. Each refusal has its error (`jwk.PrivateError`).
- `jws.Signer.fromJwk`: a private JWK as a signer, with an algorithm, or the one its `alg` names or its curve implies.
- A property over private JWKs: any bytes are refused, or read as a key whose signature its public half verifies.

### Fixed

- A key set read out of memory fails with `OutOfMemory`. A key whose members could not be allocated was left out as invalid, and a set whose keys could not be allocated was refused as `InvalidDocument`.
- `jwk.KeySet`'s copy of its document is wiped by `deinit`: it held the secret members the document had (an `oct` key's `k`, private members left out) in memory freed unwiped.

## [0.3.0] - 2026-10-17

### Breaking

- `oauth.client_auth.Method` and `Credentials` gain `client_secret_jwt`, `jws.Signer` gains `external`, `oauth.errors.Code` gains `invalid_target` and `insufficient_user_authentication`, `oauth.token.Grant` gains `token_exchange` and `jwt_bearer`: an exhaustive switch over any of them needs the new cases.

### Added

- MCP's enterprise-managed authorization, as the Identity Assertion JWT Authorization Grant (draft-ietf-oauth-identity-assertion-authz-grant-04) gives it: `oauth.requestIdJag` exchanges the user's token at an identity provider (an ID token, a SAML assertion or a refresh token) for an ID-JAG (RFC 8693), checked for exactly what was asked (the provider as issuer, the authorization server as its sole audience, the client, the resource alone, no scope beyond the request, unexpired, no `authorization_details`); `oauth.redeemIdJag` redeems it with that authorization server (RFC 7523), the assertion alone carrying scope and resource, and holds the access token to Bearer, the resource and the assertion's scope, keeping no refresh token. The messages in `oauth.id_jag`, sans I/O.
- `oauth.jwtBearer`: a JWT as the grant (RFC 7523 §2.1), with a client or with none, for a workload's identity token (MCP's workload identity federation).
- `oauth.exchange`: token exchange (RFC 8693), its request as `token.Grant.token_exchange` and its answer read (`readResponse`), the token type identifiers.
- `client_secret_jwt` client authentication (an HS256 assertion under the client's secret), and `jws.Signer.external`: a signer outside the process (a KMS, an HSM) that signs the input clearance built, for `private_key_jwt` or any JWT.
- `jws.inspect` and `jwt.inspect`: a token read and its type and claims checked under `verify`'s bounds and rules, its signature not verified, for a holder that passes it to the party that verifies it.
- Properties over `inspect`, the exchange's answer, the identity provider's answer and the redemption's.

### Changed

- `oauth.requestToken`, `oauth.token.request` and `oauth.client_auth.formRequest` take the client as optional: null sends no client, for a grant that is its own credential. Passing a client is unchanged.

## [0.2.3] - 2026-10-17

### Added

- `oauth.registration.ClientMetadata.application_type` (`native` or `web`, OpenID Connect Dynamic Client Registration §2), which MCP asks every client to name when it registers.

### Changed

- A registration that gives a secret without `client_secret_expires_at` is read, its expiry null, where it was refused: RFC 7591 requires the member, servers leave it out (the MCP conformance suite's authorization server among them), and its absence says nothing a client acts on.

## [0.2.2] - 2026-10-17

### Changed

- `oauth.bearer.Verifier` answers a token its authorization server will not introspect (`unsupported_token_type`, which oidc-provider gives for the JWT access tokens it issues) with 401 `invalid_token`, the client's to fix, instead of failing with `error.Unavailable` (a 503), which is kept for a server refusing the resource server's credentials or failing. Found running the flows against oidc-provider.
- `oauth.token.readResponse` and `TokenSet.read` no longer zero their 8 KiB stack scratch before each parse: it was set up from a struct literal, which fills the whole buffer first, and that fill was half the time of reading a 1 KiB response on Linux. The scratch is now set up in place (389 to 217 ns per response on the Lima VM, 325 to 224 ns on an M3, best of 7). `errors.Text.init` the same way.

## [0.2.1] - 2026-10-17

### Changed

- `oauth.token.readResponse` and `TokenSet.read` parse a response of up to 2 KiB on the stack, wiping only what the parser wrote (the strings it unescaped), instead of allocating and wiping a heap buffer of twice the body and 4 KiB: one allocation per response (the set's own) and about a fifth less time (433 to 352 ns for a 1 KiB response on an M3). Larger responses still parse in wiped heap memory.
- The benchmarks time OAuth's messages: a token response read, RFC 8414's example metadata read, an authorization URL written.

## [0.2.0] - 2026-10-17

### Breaking

- Two modules: `clearance` is JWT and JOSE alone, on std, aegis, strand and cloak; OAuth 2.1 is the module `clearance.oauth` (the messages that were `clearance.oauth`, and the flows), built when a project sets the build option `oauth`. uplink is a lazy dependency, fetched only then: a project that verifies and signs tokens fetches no uplink.

### Added

- `clearance.oauth`, the flows on uplink's client, each request to an endpoint held to HTTPS, no redirect followed, each answer bounded and read into wiped memory when it carries secrets: `discover` (RFC 8414 and OpenID Connect locations in MCP's order, a 4xx trying the next, an issuer mismatch failing at once); `discoverResource` (RFC 9728, from a challenge's `resource_metadata` or the inserted then the root location); `bearerChallenge` (a 401's or 403's Bearer challenge from its `WWW-Authenticate` lines, for a step-up); `AuthorizationFlow` (`begin` draws the state, the PKCE verifier and the nonce and writes the URL; `finish` reads the redirect, `state` then RFC 9207's `iss`, and exchanges the code with the RFC 8707 resources); `requestToken`, `refresh` (the granted scope and refresh token kept when the answer leaves them out), `clientCredentials`, `register` (RFC 7591, with an initial access token); `fresh` (a store's tokens refreshed and saved when they near expiry, forgotten when the grant is spent); `RemoteKeySet` (a `jwks_uri` kept for its `Cache-Control` lifetime clamped to 5 minutes..24 hours, fetched again for an unknown `kid` at most once per cooldown, one fetch for every waiter, the set held kept through a failing key server for a grace, keys leased so a fetch never frees keys in use; `verify`); `Introspector` (RFC 7662 answers kept until the earlier of `exp` and a bound, keyed by the token's SHA-256, the count bounded).
- `id_token`: OpenID Connect ID tokens checked as OpenID Connect Core 3.1.3.7 asks: `iss` byte for byte, the client among the audiences and any other one trusted, `azp` the client and required beside several audiences, `sub`, `exp` and `iat` present (`iat` not in the future), the request's `nonce` in constant time, `auth_time` within `max_age`, `at_hash` the access token's (SHA-512 for EdDSA); a token typed other than `JWT` refused. `accessTokenHash` (Core A.3's value in the tests).
- `access_token`: JWT access tokens as RFC 9068 profiles them: `at+jwt`, the issuer, this resource as the audience, `sub`, `client_id`, `iat` and `jti` present, `scope` read, a key-bound token (`cnf`) refused; `hasScopes`.
- `jwt.Verified.rest`: the scratch still free, for a profile reading more of the payload; `jwt.numericDate` public.
- `clearance.oauth.bearer.Verifier`: a resource server's check of `Authorization: Bearer` (RFC 6750 §2.1, a b64token, never the query) as a JWT access token through a `RemoteKeySet` (fetched again once for an unknown key) or by introspection (active, unbound, unexpired, the issuer, this resource among the audiences), then the scopes needed; a refusal carries its status (400, 401, 403) and the challenge to write (`error`, `scope` for a step-up, `resource_metadata`). `AuthorizationFlow.verifyIdToken`: the ID token a code flow brought, with the flow's nonce and the access token's hash.
- `oauth.store`: the `TokenStore` interface (load, save, forget by key) and a store in memory.
- End-to-end tests against an authorization server on uplink's server in the same process; the `discover` example, run by hand against Google, Microsoft and GitHub Actions.

### Changed

- Depends on uplink 0.8.1, lazily, with its client (for `wire.cache`).

## [0.1.1] - 2026-10-17

### Added

- `oauth`: OAuth 2.1's messages, sans I/O, on `uplink.wire`. `url`: endpoints held to HTTPS (HTTP to loopback alone), issuers, the metadata locations of RFC 8414, OpenID Connect Discovery and RFC 9728 in MCP's order, a resource matched exactly or as an ancestor, and client ID metadata document URLs checked. `metadata`: authorization server and protected resource metadata read, the issuer compared byte for byte and the resource as the caller's rule says, every endpoint checked; protected resource metadata written. `pkce`: S256 alone, verifiers and `state`/`nonce` values from `io`, compared in constant time. `authorize`: the authorization URL (RFC 8707 resources, the endpoint's own query kept) and the callback read: `state`, then RFC 9207's `iss` (compared as a string, required when advertised, checked when sent anyway), then the code or the error; a parameter twice refused. `client_auth`: none, `client_secret_basic` (id and secret form-encoded first), `client_secret_post` and `private_key_jwt` (its audience the issuer), chosen from the server's list; form requests in wiped memory. `token`: the code, refresh and client-credentials grants; responses read into a `TokenSet` whose tokens live in wiped memory, expiry from the moment read, the requested scope and the previous refresh token kept when the response leaves them out, a type other than Bearer refused; a set written and read for a store. `registration`: RFC 7591 requests and responses (a secret with no expiry refused), client ID metadata documents written. `introspection`: RFC 7662 requests and responses, the audience one or several, a key-bound token marked. `challenge`: Bearer challenges read (with `resource_metadata`) and written, and a step-up's scope. `errors`: an OAuth error response as a value with its text inline.
- Properties over every OAuth reader (metadata, token, registration and introspection responses, the callback, challenges), fuzzed in the release tier.

### Changed

- Depends on uplink 0.8.0 for `uplink.wire` alone (`.client = false`: uplink's client and what it fetches stay out).

## [0.1.0] - 2026-10-17

### Added

- `jws`: the compact serialization split by its two dots before anything is decoded (a third refused, a size limit first), the protected header read under limits, `crit` refused, and the signature verified against the caller's keys with HS256/384/512, RS256/384/512, PS256/384/512, ES256, ES384 and EdDSA (Ed25519, as `EdDSA` and as `Ed25519`). The caller names the allowed algorithms; there is no `none`. The key is chosen by `kid` among the caller's keys, never from the header's `jwk`, `jku`, `x5u` or `x5c`. Verification allocates nothing: the decoded parts live in a scratch buffer. `Diagnostics` names the check that refused. `sign` writes a compact JWS with an HMAC secret or a cloak private key.
- `jwk`: JWKs and JWK sets read into keys (RSA of 2048 to 4096 bits, EC P-256 and P-384 with the point checked on its curve, OKP Ed25519, and `oct` when asked), each checked as read; keys that cannot be used are left out and counted by reason, two keys with one `kid` both left out, private members refused, a set mixing secret and public keys refused. Thumbprints (RFC 7638) and their URIs (RFC 9278).
- `jwt`: claims read by type before value (a registered claim of the wrong JSON type refuses the token), `exp` required unless the validation says otherwise, `nbf`, `iat` and `max_age` with a bounded leeway, `iss`, `sub` and `aud` (a token with an audience refused by a verifier that names none), explicit typing (`at+jwt`, `dpop+jwt`), custom claims decoded into the caller's type; `sign`.
- Tests: RFC 7520, 7638 and 8037 examples; Wycheproof's `json_web_signature`, `json_web_key` and `json_web_crypto` files (465 of 475 cases as the files say, 10 diverging by decision, each named in the harness); properties over tokens, key sets and claims, fuzzed in the release tier.
